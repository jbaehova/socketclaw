# SocketClaw 구현 및 검증 보고서

작성일: 2026-09-29

범위: completion PLAN, PRD, TRD에 따른 로컬 작업 트리 변경

판정: 주요 기능 구현과 로컬 검증을 완료했다. 전체 출시 게이트는 아직 통과하지 않았다.

## 반영한 기능

| 요구사항 | 구현 | 검증 근거 |
| --- | --- | --- |
| FR-01, FR-02 알림 신뢰성 | 스키마 6의 사건 전이 트리거와 같은 DB outbox, 레거시 ID 이전, 목적지 보류 및 명시적 대조 | 복원 후 첫 알림, 트랜잭션 rollback, 55개 구 목적지 뒤 새 알림, 레거시 목적지 불확실성 회귀 |
| FR-03, FR-04 상시 수집과 제어 | ApplicationService, 같은 UID의 Unix 소켓, 세션과 복원 세대 검증, 명령 영수증 및 공유 트랜잭션 | 별도 소유자 프로세스, 응답 재요청 중 메모 중복 방지, 다른 UID와 초과 프레임 거절 |
| FR-05 조사와 긴 작업 | 소유자에서 조사 중복 방지, 내보내기 및 진단 작업 ID, 중단 상태 보존 | 클라이언트 교체 후 조사 유지, 소유자 종료 시 불확실한 제공자 결과 기록, export 작업 조회 |
| FR-06, FR-07 기록 관리 | 백업 하나를 사용하는 온라인 분할 정리, 취소와 재개, 백업 목록과 pin, 복원 journal과 설정 확인 | 정리 보호, 취소와 동일 백업 재개, 백업 실패 시 삭제 0건, 최초 홈 복원 중단 복구 |
| FR-08 서비스 상태 | 서비스별 인덱스 조회, 설정 지문과 신선도, timeout 변경 시 streak 초기화 | 다른 이벤트 1만 건 뒤 기존 서비스 조회, 설정 변경 회귀 |
| FR-09 제품 범위 | 지정 호스트와 서비스 및 파일 로그 감시로 문구 통일, 지원하지 않는 수집 명시 | README, 기존 onboarding 범위 안내, CLI 도움말 |
| FR-10 작업 흐름 | 공용 사건 화면, /storage, 별도 수집 종료 확인, 설정 오류의 Health 표시 | 두 터미널 크기의 연결 TUI에서 확인, 메모, 종료, 내보내기 및 독립 수집 유지 |
| FR-11 검증 체계 | 실제 프로세스 부하 도구, TLS 격리 인증서, webhook 실패 재시도, 온라인 정리, 수동 플랫폼 workflow | 로컬 단기 실행 완료. 양쪽 플랫폼 72시간과 외부 사용자 과업은 미완료 |

새 구현은 `application.py`, `control.py`, `gateway.py`, `unit_of_work.py`,
`completion_schema.py`, `maintenance.py`와 `ui/operations.py`에 모았다.
기존 저장소와 화면을 재사용해 독립 TUI 및 연결 TUI의 도메인 검증을 공유한다.
`attach --tui`의 기존 읽기 전용 모드도 유지한다.

## 실제 실행한 검사

- Python 3.11.15와 Python 3.14.7 전체 검사: 각각 687개 통과, 명시적 유료 AI 검사 1개 skip, 스냅샷 36개 통과.
- 이후 중복 방지 기록 보존, 백업 pin 보호와 응답 정지 감지 회귀 3개를 추가했다. 이들을 포함한 Python 3.14 관련 회귀 28개와 Python 3.11 완료 계약 회귀 26개도 통과했다.
- Ruff 검사 및 형식 검사 통과. Pyright strict 오류 0개.
- 잠금 의존성 감사 결과 알려진 취약점 0개.
- wheel과 sdist 빌드 후 별도 환경에 잠금 의존성으로 wheel 설치. IPv4와 IPv6 loopback 검사 및 연결 PTY 통과.
- macOS arm64 독립 실행 파일 빌드와 실제 PTY 검사 8개 통과.
- 실제 PTY에서 초기 설정, 취소, 기존 설정 시작을 80×24와 120×36에서 실행했다. 60×18 축소와 재확대 및 종료도 통과했다.
- 연결 PTY에서는 /storage 진입, 크기 변경, 뷰어 종료 후 수집 유지와 명시적 소유자 종료를 두 크기에서 확인했다.

유료 검사의 skip은 통과로 계산하지 않는다. 현재 소스의 Linux CI나 Intel macOS
배포물 검증을 과거 v0.6.0의 성공 기록으로 대체하지 않는다.

## 용량과 부하 측정

측정 환경은 macOS 27 arm64, Python 3.11.15다. 다른 작업의 간섭 여부를 구분한다.

| 기록 규모 | 총 기록 | 삭제 대상과 실제 삭제 | 정리 | 복원 |
| --- | ---: | ---: | ---: | ---: |
| 30일, 하루 18,720건 | 561,601 | 37,440 / 37,440 | 20.78초 | 18.14초 |
| 90일, 하루 18,720건 | 1,684,801 | 1,160,640 / 1,160,640 | 332.57초 | 28.63초 |

위 용량 검사는 정리 대상 전체 삭제와 재시작 및 전체 행 수 복원을 확인했다.
정리 시간은 중복 방지 기록을 executemany로 바꾸기 전 측정이며, 최종 코드의 속도
보장으로 사용하지 않는다. 배치 변경 뒤에는 취소, 재개와 보호 규칙 회귀를 재검증했다.

첫 단기 부하는 초당 100건을 60초간 넣어 6,000건 모두 중복 없이 저장했고 공백은 0건이었다.
TLS와 webhook을 추가한 30초 검사에서는 3,000건 모두 저장됐다. webhook 6건은 첫 시도
실패를 주입한 뒤 12번의 요청으로 모두 전달됐다.

대용량 용량 검사와 동시에 실행한 후속 60초 검사에서는 입력 6,000건과 온라인 정리
6,200건을 모두 처리했지만 HTTP 간격 p95가 2.547초로 목표를 넘었다. 이 실행은 실패로
보존했다. 간섭을 제거한 실행에서도 TCP p95 2.229초가 나와 실패를 유지했다.
이후 수집기 상태 저장과 관측 저장을 같은 비동기 잠금에 대기시키도록 바꿨다.
수정 후 60초 실행은 로그 6,000건과 정리 6,200건을 모두 처리했고 공백은 0건이었다.
서비스 간격 p95는 HTTP 1.448초, HTTPS 1.194초, TCP 1.243초로 통과했다.
RPC p95는 316.69ms였다. webhook은 6건 모두 전달됐고 최초 실패를 포함한 시도는 12번이었다.
60초 실행에는 로그 회전이 발생하지 않았다. 이 결과를 30분 또는 72시간 결과로 간주하지 않는다.

최종 빌드 파일의 SHA-256과 잠금 파일 해시는 `build-manifest.json`에 기록했다.
개인 증거 산출물은 gitignore에 포함된 `artifacts/completion/` 아래에 둔다.
원본 DB나 비밀키를 공유 문서에 포함하지 않는다.

## 재현 절차

`src` 디렉터리에서 실행한다.

```sh
uv sync --dev --locked
uv run --locked python -m ruff check .
uv run --locked python -m ruff format --check .
uv run --locked python -m pyright
uv run --locked python -m pytest
uv run --locked python scripts/pty_smoke.py
uv run --locked python scripts/benchmark_operations.py --batches 1 --history-days 30 90
uv run --locked python scripts/completion_validate.py --seconds 1800 --rate 100
```

72시간 실행 명령은 다음과 같다. 같은 후보를 macOS arm64와 Linux x86_64에서 각각 실행한다.
프로파일은 로컬 대상, TCP/HTTP/HTTPS와 파일 두 개를 사용한다. 300초 후부터 30분간
초당 100건을 입력하며 그 외에는 초당 1건을 입력한다. 시스템 인증서 저장소는 변경하지 않는다.

```sh
uv run --locked python scripts/completion_validate.py \
  --seconds 259200 --rate 1 --burst-seconds 1800 \
  --output artifacts/completion/owner-72h.json
```

도구의 `passed`는 해당 실행의 입력 대조, webhook 대조, 정리 완료와 서비스 간격에 대한
판정이다. `release_72h_gate`는 별도의 RSS 추세 및 과업 검토 전까지 미판정으로 남긴다.
일반 GitHub 호스팅 작업의 실행 시간 제한을 고려해 수동 workflow는 60초 또는 30분
프로필만 제공한다. 72시간은 중단되지 않는 별도 실행 환경에서 수행한다.
