# SocketClaw 완성 릴리스 TRD

작성일: 2026-09-29

상태: 구현 반영 기술 계약, 실행 근거는 구현 보고서 참조

연결 문서: [PRD](completion-prd.md), [실행 계획](completion-plan.md)

새 모듈과 명령은 이번 작업 트리에 구현했다. 배포된 v0.6.0에 이미 포함됐다는 뜻은 아니다. [구현 보고서](completion-report.md)에서 실제 검증 범위와 남은 차이를 확인한다. 요구사항 ID와 출시 기준의 원본은 PRD이며, 이 문서는 그 요구사항을 구현할 계약을 정한다.

## 1. 주요 설계 결정

| 결정 | 채택안 | 이유 |
| --- | --- | --- |
| D-01 | 수집 프로세스가 애플리케이션 홈의 유일한 쓰기 소유자가 된다 | 수집과 운영 조작을 함께 처리하면서 기존 잠금과 데이터 보호 원칙을 유지한다 |
| D-02 | 같은 계정의 로컬 Unix 소켓으로 운영 제어 요청을 전달한다 | macOS와 Linux의 로컬 사용 범위에 맞고 외부 네트워크 서버가 필요 없다 |
| D-03 | TUI에 있는 조사 및 설정 변경 로직을 공용 애플리케이션 서비스로 옮긴다 | 독립 실행과 연결 실행이 동일한 검증 및 저장 경로를 사용한다 |
| D-04 | 알림 outbox를 주 증거 DB에 통합한다 | 사건과 알림을 한 트랜잭션으로 저장하고 하나의 백업으로 복원한다 |
| D-05 | 기록 정리를 영속 작업으로 관리한다 | 작업당 백업 하나로 분할 삭제와 재개를 지원한다 |
| D-06 | 서비스별 최신 관측을 인덱스로 직접 조회한다 | 전체 이벤트 목록 제한과 서비스 상태를 분리한다 |

연결 화면이 SQLite에 직접 쓰는 방식은 채택하지 않는다. 사건 편집만 잠금을 우회하게 만들면 설정 적용과 조사 실행의 소유권이 서로 달라진다. 반대로 원격 서버나 메시지 브로커를 추가할 필요도 없다. 이번 운영 제어는 동일 컴퓨터와 동일 계정 안에서만 제공한다.

## 2. 프로세스와 모듈 구성

```text
독립 TUI ── ApplicationService 직접 호출 ── ApplicationService ── Repository
                                      │
                               Monitor / AI / Outbox

연결 TUI ── Unix socket ── ControlServer ── ApplicationService
읽기 전용 attach ── read-only Repository         │
                                      headless monitor owner
```

두 그림은 동일한 공용 서비스를 사용하는 대체 실행 모드다. 한 홈에서 두 소유 프로세스를 동시에 실행하지 않는다. 일반 TUI 소유 모드에서도 같은 서비스 경계를 사용하지만 제어 서버 공개는 이번 범위에서 headless 모드에 한정한다.

| 현재 위치 | 변경 책임 |
| --- | --- |
| `cli.py` | 실행 소유권과 종료 처리, 연결 모드 선택, 유지보수 명령 라우팅 |
| `ui/app.py` | 화면과 세션 초안 관리. 조사 실행 및 저장 로직은 공용 서비스에 위임 |
| 새 `application.py` | 사건 조작, 설정 변경, 조사 수명, 수동 진단과 내보내기의 공용 진입점 |
| 새 `control.py` | 프로토콜 검증, 로컬 소켓 수명, 요청 분배와 연결 상태 |
| 새 `gateway.py` | 독립 실행과 연결 실행에 공통인 타입 인터페이스 및 DTO |
| `ui/attached.py` | 기존 읽기 전용 화면 유지. 제어 모드는 공용 작업 화면을 사용 |
| `storage.py`, `incident_store.py`, `migrations.py` | 스키마 6, 원자적 명령 반영, outbox와 정리 작업, 최신 서비스 조회 |
| `notifications.py` | 주 DB outbox 송신과 재시도. 기존 행 번호 스캔 제거 |
| 새 `maintenance.py` | 백업 검사, 온라인 정리 작업, 복원 및 백업 관리 |
| `ui/services.py`, `ui/health.py`, `ui/dashboard.py` | 최신 측정 및 신선도, 연결과 알림 상태, 감시 범위 표시 |

이 분리는 파일을 이동하는 것만으로 완료되지 않는다. 현재 `ui/app.py`가 갖고 있는 조사 중복 방지와 취소 처리도 소유 프로세스로 이전해야 한다. 연결 TUI가 닫혀도 소유 프로세스가 접수한 조사는 계속 실행된다.

## 3. 실행 모드와 수명 계약

| 명령 | 동작 |
| --- | --- |
| `socketclaw` | 기존 독립 TUI. 소유자가 이미 있으면 연결 명령을 안내하고 종료 |
| `socketclaw monitor` | 홈 잠금을 획득하고 수집기, 제어 서버, 조사 작업자 및 알림 작업자를 시작 |
| `socketclaw attach` | 기존 읽기 전용 상태 조회 |
| `socketclaw attach --tui` | 기존 읽기 전용 화면 |
| `socketclaw attach --tui --control` | 공용 작업 화면을 제어 클라이언트로 실행. 소유자가 없으면 자동 수집 시작 없이 실패 |
| `socketclaw monitor-stop` | 제어 서버에 명시적 정상 종료 요청. TUI에서는 별도 확인 후 같은 요청 |

제어 모드의 `Q`와 `Ctrl+C`는 연결만 종료한다. 수집 일시정지와 프로세스 종료는 다른 동작으로 표시한다. 단순 연결 때문에 `start_run`, 마이그레이션 또는 미완료 조사 복구를 호출하지 않는다.

소유자 종료는 새 변경 요청 접수 중단, 진행 중 DB 커밋 완료, 수집 및 작업자 종료, 실행 기록 저장, 소켓 정리, 잠금 해제 순서다. AI 네트워크 요청은 제한 시간까지 기다리거나 기존 정책에 따라 실패로 기록한다. 이미 발생한 과금 가능성을 숨기지 않으며 재시작 시 자동 유료 재요청을 하지 않는다.

수집기 재시작 때 세션 nonce를 바꾸고 클라이언트는 capabilities와 현재 설정을 다시 읽는다. 복원 뒤에는 이전 화면에서 보낸 변경 요청을 자동 재전송하지 않는다. 먼저 증거 DB의 복원 세대가 바뀌었음을 표시하고 사용자가 현재 상태를 검토하게 한다.

## 4. 로컬 제어 프로토콜

### 4.1 전송과 접근 경계

기본 경로는 홈 아래 `control.sock`이다. 부모 디렉터리는 0700, 소켓은 0600으로 만들며 소유 계정을 검증한다. 심볼릭 링크와 다른 유형의 기존 경로는 거절한다. 오래된 소켓은 홈 잠금을 획득한 소유자만 제거한다. 경로가 OS 한도를 넘으면 명시적 오류와 짧은 홈 경로 사용법을 제공하며 공용 임시 디렉터리로 조용히 이동하지 않는다.

서버는 같은 UID의 연결만 허용한다. 플랫폼별 peer credential 검사를 실제 macOS/Linux 테스트로 검증하고 미지원 환경에서 제어 모드를 실패 처리한다. Windows에는 TCP 대체 서버를 자동으로 열지 않는다. API 키는 소켓 로그와 요청 결과에 포함하지 않는다.

프로토콜 v1은 길이 접두어가 있는 UTF-8 JSON 메시지를 사용한다. 기본 프레임 최대 1 MiB, 동시 연결 최대 8개, 클라이언트별 진행 요청 최대 8개로 제한한다. 큰 결과는 기존 페이지 단위로 조회하고 내보내기는 소유자 쪽 파일로 생성한다. 임의 Python 속성 호출, SQL 또는 셸 명령 전송은 허용하지 않는다.

### 4.2 요청 및 응답

```json
{
  "protocol": 1,
  "request_id": "uuid",
  "owner_session": "nonce",
  "database_generation": "uuid",
  "method": "incidents.change_status",
  "params": {
    "incident_id": "uuid",
    "expected_revision": 7,
    "status": "resolved",
    "reason": "서비스 복구 및 후속 관측 확인"
  }
}
```

응답은 `request_id`, `status`, `result` 또는 구조화된 `error`를 포함한다. 오류 코드는 `validation`, `conflict`, `not_found`, `read_only`, `busy`, `owner_unavailable`, `version_mismatch`, `recovery_required`로 구분한다. 오류에 원본 비밀정보를 포함하지 않는다. 호환하지 않는 버전은 변경 요청을 보내기 전에 연결을 거절한다.

| 메서드 묶음 | 계약 |
| --- | --- |
| `hello`, `health.get`, `request.get` | 버전과 기능 확인, 작업자 상태, 접수 결과 조회 |
| `repository.*`, `incidents.*`, `investigation.context` | 기존 필터와 커서 페이지 조회, 상세 증거 및 전송 문맥 미리보기 |
| `incidents.change_status`, `incidents.add_note`, `repository.record_action` | 기존 도메인 검증 및 충돌 검사로 기록 |
| `repository.update_response_proposal_status`, `incidents.create_suppression`, `incidents.disable_suppression` | 명시적 검토와 예외 관리. 자동 실행 없음 |
| `investigation.request`, `investigation.retry` | 유료 실행은 명시적 요청만 접수. 작업 ID를 즉시 반환 |
| `config.get`, `config.update`, `credential.set` | 비밀정보를 제외한 설정 조회, revision 기반 변경, 반환하지 않는 자격증명 저장 |
| `monitor.pause`, `monitor.resume`, `diagnostic.request` | 스케줄 제어와 대상별 잠금을 공유하는 수동 검사 |
| `export.request`, `retention.*`, `owner.stop` | 영속 작업 생성, 진행 조회 및 명시적 종료 |

설정 변경은 화면에서 계산한 전체 설정으로 덮어쓰지 않는다. `base_revision`과 변경 필드 집합을 보내고 소유자의 최신 설정에 검증 후 적용한다. 충돌 응답은 재검토 안내를 반환한다. 클라이언트는 config.get으로 최신 설정과 revision을 다시 읽고 작성 중인 초안을 유지한다. 파일 저장과 런타임 재설정 중 장애가 발생하면 저장된 설정을 기준으로 재조정하고 불일치를 Health에 표시한다.

### 4.3 재시도와 트랜잭션

`command_receipts`에 요청 ID와 정규화된 입력 해시를 보관한다. 동일 ID와 동일 입력이면 저장한 결과를 반환하고, 동일 ID에 다른 입력이면 거절한다. 메모 및 조치 UUID도 기존 멱등성 검사를 유지한다. 짧은 DB 변경은 영수증과 도메인 변경을 같은 트랜잭션에 저장한다. 현재 각 메서드 내부에서 커밋하는 구조는 공유 unit-of-work를 받을 수 있도록 분리한다.

AI와 내보내기 등 긴 작업은 접수 기록과 영속 작업 ID를 먼저 저장한다. 연결 타임아웃을 작업 취소로 해석하지 않는다. AI 요청 전후 프로세스가 죽어 제공자 처리 여부를 알 수 없으면 `interrupted/unknown_outcome`을 표시하고 사용자만 재시도한다. 사건별 활성 조사 중복 방지를 소유자에서 수행한다.

자격증명 변경은 비밀 원문이나 일반 해시를 영수증에 저장하지 않는다. 서버 비밀키를 이용한 입력 지문과 접수 상태만 저장하고 파일 쓰기는 기존 원자 교체 방식으로 처리한다. 파일 쓰기 직후 장애의 불확실성은 현재 자격증명 상태를 재검사해 해소한다. 영수증 응답은 자격증명 존재 여부만 반환한다. 파일 작업 후 종료된 요청의 영수증이 accepted 상태라면 자동 반복하지 않는다. request.get과 config.get으로 상태를 확인하고 새 요청 여부를 정한다.

## 5. 스키마 6과 알림 복구

### 5.1 새 데이터 구조

| 테이블 또는 변경 | 주요 필드와 제약 |
| --- | --- |
| `deliveries` | 안정적인 delivery ID, transition ID, 채널, destination revision, 최소 payload, 시도 횟수, 다음 시도, 전달 시각, 오류 및 lease |
| `notification_metadata` | 레거시 import 완료 표식과 검증 결과. outbox 작업자 상태 |
| `command_receipts` | request ID 기본키, 메서드, 입력 지문, 상태, 결과 참조, 접수 및 완료 시각 |
| `maintenance_jobs` | 작업 ID, 상태, cutoff, watermark, 백업 경로와 해시, 삭제 건수, 진행 위치, 오류 |
| `events` 확장 | nullable `service_id`, `service_scope_hash` 및 `(service_id, ingest_seq DESC)` 인덱스 |
| `schema_meta` 확장 | DB identity, restore generation, 설정 revision 연결 정보 |

스키마 1부터 5까지의 기존 경로 뒤에 5→6 마이그레이션을 연결한다. 과거 점수와 사건 기록을 다시 해석하지 않는다. 서비스 식별자는 검증된 기존 evidence에서만 추출하고 정책 지문을 확정할 수 없는 과거 행은 unknown으로 둔다.

### 5.2 사건과 알림의 원자적 저장

알림 대상 전이를 저장하는 트랜잭션에서 활성 채널의 delivery 행도 생성한다. 중복 방지는 `(transition_id, channel, destination_revision)`의 유일성으로 보장한다. 일반 관측마다 알림을 만들지 않고 현재와 같은 사건 생성, 악화, 재발, 관측된 복구를 대상으로 한다.

알림 비활성 중 발생한 과거 전이를 설정 활성화만으로 대량 전송하지 않는다. 설정 변경 시점 이후 새 전이부터 적용한다. 기존 pending 항목은 채널을 껐을 때 보류하며 다시 켜도 목적지가 변경됐다면 새 주소로 자동 전송하지 않는다. 보류 항목은 사유와 개수를 표시하고 사용자가 취소 또는 기존 목적지 재시도를 선택한다. 과거 목적지 정보는 사설 설정으로 보호하고 공유 보고서에 포함하지 않는다.

작업자는 짧은 트랜잭션으로 항목을 claim하고 네트워크 요청은 트랜잭션 밖에서 실행한다. 성공 및 실패는 다시 짧은 트랜잭션으로 기록한다. 소유자 장애 뒤 만료된 lease는 재시도할 수 있다. 작업자 heartbeat와 last error는 전달 실패 건수와 별도로 보여준다.

외부 수신과 로컬 커밋을 하나의 트랜잭션으로 묶을 수 없으므로 전달 보장은 at-least-once다. `Idempotency-Key`는 delivery ID로 고정한다. 복원 뒤 같은 전이가 재전송되면 같은 키를 사용한다. 웹훅 수신자는 중복을 제거할 수 있지만 로컬 알림의 중복 표시는 남을 수 있다.

### 5.3 기존 notifications.db 이전

1. 홈 잠금 아래 주 DB와 기존 알림 DB를 각각 검증하고 마이그레이션 전 백업 묶음을 만든다.
2. 주 DB에 존재하는 transition ID를 기준으로 기존 전달 및 pending 상태를 가져온다. 기존 delivery ID를 보존해 수신자의 중복 제거 키를 바꾸지 않는다. 기존 커서보다 앞뒤인지로 누락 대상을 판단하지 않는다.
3. 기존 알림 채널이 활성 상태면 주 DB의 알림 대상 전이를 ID로 대조해 delivery가 없는 항목을 복구 대상으로 만든다. 오래된 항목은 지연 증거로 표시한다. 중복 전송 가능성과 예상 건수를 이전 결과에 남긴다.
4. 기존 알림 DB가 없거나 손상돼 상태를 확인할 수 없으면 `reconciliation_required`를 표시한다. 수집은 계속하되 역사적 전이의 전송 여부를 임의로 확정하지 않는다. 현재 migration watermark 이후의 새 사건은 정상 enqueue한다.
5. 주 DB에 없는 기존 delivery는 보류 보관하고 자동 전송하지 않는다. import 표식과 주 DB 변경을 한 번에 커밋한다.
6. 검증된 사본은 backups에 보관한다. 원래 notifications.db도 보존하되 이후 송신에는 사용하지 않는다. 주 DB의 import 완료 표식으로 재수입을 막는다. 레거시 webhook에는 목적지가 없으므로 미전달 건은 명시적인 역사 알림 대조 전까지 보류한다.

현재 결함이 이미 발생한 홈도 이 대조 과정으로 복구한다. 알림 상태를 알 수 없는 기록은 정상 처리로 간주하지 않고 사용자가 대조 결과를 확인하게 한다.

### 5.4 백업 복원

`socketclaw db restore --backup PATH`는 미리보기, `--apply`는 실제 복원으로 설계한다. 소유자가 실행 중이면 중지 안내와 함께 거절한다. 무결성, manifest 해시와 지원 스키마를 확인한 뒤 현재 DB를 검증된 구조 백업으로 보존한다. WAL에 커밋된 내용까지 포함한 백업을 만든 후 기존 DB 및 sidecar를 별도 경로로 이동하고 staging DB를 원자 교체한다.

복원 단계별 journal을 남겨 중간 장애 후 원본 또는 복원본 중 하나로 명시적으로 복구한다. 성공하면 restore generation을 갱신해 기존 클라이언트 요청이 새 이력에 적용되지 않도록 한다. 알림 delivery 상태는 주 DB와 같이 돌아가므로 외부로 이미 보낸 알림이 중복될 수 있지만 복구 후 새 사건을 과거 커서 때문에 건너뛰지 않는다.

스키마 5 이하 백업은 복원 후 6으로 이전한다. 이때 현재 홈에 남은 레거시 알림 DB를 복원본과 무조건 합치지 않고 같은 ID 대조 및 `reconciliation_required` 절차를 적용한다. 백업에는 API 키와 현재 설정 파일이 포함되지 않는다. 설정 지문 불일치를 보여주고 사용자가 현재 수집 범위를 확인한 뒤 수집을 재개한다.

## 6. 온라인 기록 정리와 백업 관리

### 6.1 사용자 명령과 영속 상태

`history-retention --days N`은 읽기 전용 미리보기다. `--apply`는 정리 작업을 시작하고 작업 ID를 반환한다. `--status JOB`, `--cancel JOB`, `--resume JOB`으로 조작한다. headless 소유자가 있으면 제어 서버로 보내고 소유자가 없으면 기존 잠금 아래 같은 공용 서비스를 실행한다. 일반 TUI가 소유한 홈은 TUI 내 정리 화면을 사용하도록 안내한다.

상태는 `planned → backing_up → running → completed`이며 `paused`, `failed`, `cancelled`를 별도로 기록한다. 한 홈에서 삭제 작업은 하나만 실행한다. 취소는 현재 트랜잭션을 마친 뒤 적용하고 남은 대상은 삭제하지 않는다.

### 6.2 대상과 백업 경계

SQLite backup API로 일관된 스냅샷을 만들고 그 백업 안에서 읽은 `ingest_seq` 최댓값을 작업 watermark로 확정한다. 대상은 고정 cutoff 이전이면서 watermark 이하인 기존 정상 기록이다. 이후 유입된 관측은 이번 작업에 포함하지 않는다. 백업이 성공하고 해시와 무결성을 검증하기 전에는 삭제를 시작하지 않는다.

백업 중에는 수집 커밋을 장기간 막지 않도록 페이지 단위 복사를 사용한다. 시작 전 공간 검사는 추정 DB 크기 두 배와 256 MiB 여유 공간을 기본 요구로 한다. 실제 공간 부족은 단계별 오류로 처리하며 자동으로 과거 백업을 지우지 않는다.

기본 배치 크기는 1,000행으로 시작한다. 각 배치는 짧은 쓰기 트랜잭션으로 완료하고 이벤트 루프에 실행권을 돌려준다. 단일 배치 잠금 100 ms 초과 시 다음 배치를 줄이며 정상화 후 상한 1만 행까지 조정한다. 이 수치는 구현 검증 대상이며 100 ms를 절대 보장하는 문구로 노출하지 않는다.

삭제 직전에 사건 링크와 조사 참조를 다시 검사한다. 응답 제안과 suppression 결정이 참조한 증거도 보호한다. 여기에 서비스별 마지막 관측과 기존 재수집 방지 기록을 보호 대상으로 추가한다. 운영 조작과 삭제가 경쟁하면 같은 DB 트랜잭션 및 외래키 검증으로 연결된 증거가 사라지지 않게 한다. 시작 시 대상 건수는 추정치로 표시하고, 작업 중 보호 대상으로 바뀐 행은 건너뛴 수에 반영한다. 최종 결과는 삭제, 보호 및 미처리 건수를 나눠 보고한다.

### 6.3 재개와 보관 한계

삭제 건수와 진행 위치는 삭제 트랜잭션에서 함께 갱신한다. 재시작 시 백업 존재와 해시, DB identity 및 restore generation을 확인한 뒤 같은 백업으로 재개한다. 복원으로 generation이 달라진 작업은 자동 재개하지 않는다. 백업을 잃었으면 새 백업 없이 삭제를 계속하지 않는다.

`backups list`는 크기와 생성 목적, 보존 여부 및 진행 작업의 참조를 보여준다. `backups prune --keep-last N --older-than-days D`는 삭제 미리보기이며 `--apply`로 적용한다. 기본 추천값은 최근 3개 유지와 30일 초과다. 사용자가 직접 적용하며 자동 삭제는 기본 제공하지 않는다. 진행 작업과 실패한 migration/restore의 복구 백업은 pin하고 명시적 해제 전에는 삭제하지 않는다.

관측 정리는 SQLite 페이지 재사용을 가능하게 하지만 파일 축소를 보장하지 않는다. 사건 증거와 dedup 기록 등 보호 데이터도 계속 늘 수 있다. 용량 화면은 활성 DB, sidecar, 백업과 보호 데이터의 크기 또는 건수를 구분하고, 자동으로 영구적인 용량 상한이 생겼다고 안내하지 않는다. offline VACUUM과 전체 아카이브 정책은 이번 범위 밖이다.

## 7. 서비스 상태 조회

`Repository.latest_service_observations(service_ids)`를 추가하고 서비스별 최대 `ingest_seq`를 인덱스로 조회한다. 최근 500개 시스템 이벤트를 가져오는 경로는 제거한다. 조회한 행은 관측 당시의 설정 지문과 측정 시각을 포함한다.

상태 DTO는 `measured_status`, `observed_at`, `scope_matches`, `freshness`, `collector_state`를 분리한다. 최근 실패 이후 마지막 성공만 보여주는 방식으로 바꾸지 않는다. `freshness`는 기존 Health의 `max(3 × interval, 10초)` 기준을 공유한다.

서비스 ID가 같아도 endpoint 또는 기대 응답 조건이 바뀌면 이전 결과를 `previous_configuration`으로 표시한다. 상태에 영향을 주는 timeout도 정책 지문에 포함하고 이름 및 표시용 정보는 제외한다. interval은 지문과 분리해 신선도 계산에 적용한다. 정책 변경 시 기존 연속 성공/실패 확인값도 초기화한다. 과거 행의 지문을 알 수 없으면 `legacy_unknown`으로 표시하고 다음 측정까지 현재 설정의 정상 판정으로 쓰지 않는다.

정리 작업은 마지막 관측을 보호한다. 서비스 삭제 후 재등록은 ID뿐 아니라 정책 지문을 비교한다. 설정된 서비스 목록과 마지막 결과는 같은 설정 revision을 기준으로 그려 화면 갱신 도중 다른 대상에 결과가 붙지 않도록 한다.

## 8. 화면과 제품 설명

Overview에는 설정한 감시 범위와 최근 수집 성공 범위를 나란히 표시한다. 지원하지 않는 native log는 수집 대상 수에 포함하지 않는다. 빈 상태에서는 서비스 추가 또는 읽을 수 있는 파일 선택으로 이어지는 명확한 행동을 제공한다.

운영 제어 화면은 기존 사건 상세와 편집 컴포넌트를 재사용한다. 헤더는 독립 실행, 읽기 전용 연결, 운영 제어 연결을 구분한다. 연결 끊김은 측정 결과의 실패와 별도 상태다. 기록은 마지막으로 받은 내용임을 표시한다. 변경 요청은 소유자 연결과 세션을 다시 확인한 뒤 전달하며, 연결 실패 때는 저장하지 않고 초안을 유지한다. 재연결 시 현재 revision을 읽고 초안을 보존한 채 충돌 여부를 판단한다.

README와 첫 실행 안내에는 감시 대상의 범위, AI 선택성, 승인과 실행의 구분을 같은 표현으로 반영한다. 새 명령 도움말과 서비스 템플릿에는 실행 모드 전환 및 종료 방법을 포함한다. 외부 heartbeat나 서비스 매니저 없이 자기 프로세스의 사망 알림을 보장하지 않는다.

Release candidate의 커밋을 고정하고 macOS arm64 및 Linux x86_64에서 각각 72시간 실행한다. Intel macOS는 배포물 PTY와 플랫폼 검사를 별도로 수행한다. 장비, OS, Python, 잠금 파일 및 동시에 실행한 작업을 기록한다. 노트북 절전은 정상 측정에서 제외하며 별도 중단 시나리오로 검사한다.

기본 프로필은 localhost 대상 1개, TCP/HTTP/HTTPS 서비스 각 1개와 파일 로그 2개다. ping은 5초, 포트 검사는 60초, 서비스 검사는 1초 간격으로 설정한다. 로그는 초당 1건을 입력하고 일정 구간에 초당 100건을 30분간 입력한다. 로그 최초 연결이 완료된 뒤 측정 입력을 시작해 기존 tail 정책에 따른 초기 생략을 누락과 혼동하지 않는다. 로컬 HTTP 수신기로 webhook 전달 키를 기록한다. 테스트용 TLS 인증서를 사용해 격리 테스트 클라이언트에 CA를 주입하고 인증서 검사를 유지한다. 실제 사용자 시스템의 인증서 저장소를 변경하지 않는다.

정상 구간과 장애 구간을 구분해 서비스 중지 및 복구, 로그 회전, 연결 재접속을 반복한다. 복원과 강제 종료, 디스크 부족은 별도 격리 홈에서 수행해 72시간 정상 수집의 연속성 측정과 혼동하지 않는다. 실제 사용자 환경에서는 지원 범위 안의 읽을 수 있는 파일과 본인 서비스만 선택한다.

다음 수치는 실행 전에 고정하는 인수 목표다.

- NFR-02, NFR-03, NFR-05의 지연과 처리 대기 기준을 만족한다. 최소 1,000회의 일반 RPC 요청을 기록해 p95를 계산한다.
- 입력 시퀀스와 저장된 source key를 대조해 설명되지 않는 누락 및 중복을 0건으로 확인한다. 장애 구간에서 관측 불가능한 네트워크 측정은 성공 수집으로 집계하지 않는다.
- 정상 마지막 24시간의 시간별 RSS 중앙값 증가 추세는 1 MiB/시간 이하이고 최대 RSS는 512 MiB 이하다. 대상 장비와 프로필에서만 적용하는 기준으로 공개한다.
- 초당 100건 구간의 5분별 최대 backlog가 1,000건을 넘지 않고 마지막 구간에 지속 증가하지 않는다. 입력 종료 30초 안에 backlog와 pending commit이 0이 된다.
- 정리와 백업 중에도 서비스 검사 간격 목표를 측정한다. 성능 기준을 초과하면 온라인 정리 구현을 수정하고 재검증한다.

### 9.3 탐지와 사용자 과업

고정 시나리오는 정상 sudo, 정상 인증 성공, 일시적 연결 실패, 확인 임계치를 넘긴 서비스 장애, 인증 실패 burst, 새 민감 포트와 유지보수 예외를 포함한다. 시나리오마다 예상 이벤트 및 사건 전이, 알림 수와 시간 범위를 테스트 전에 선언한다. 이 corpus의 기대 결과는 모두 충족해야 한다. 정답 없는 실제 운영 로그에는 임의의 precision/recall 수치를 붙이지 않는다. 로컬 탐지 점검과 AI 응답 점검도 별도로 기록한다.

구현 담당 외 사용자 최소 1명이 설치부터 오프라인 사건 종료와 내보내기까지 수행한다. 진행자가 개입한 단계는 실패로 기록하고 수정 후 다시 실행한다. 정상 운영에서 같은 원인의 불필요한 알림이 반복되면 필수 마무리 결함으로 분류한다. AI 라이브 검증은 키와 실행 허용이 있는 경우에만 진행하고 미실행은 미검증으로 표시한다. 최소 라이브 사례에서도 근거 ID와 인용 필드의 일치, 가설과 사실의 구분, 근거 없는 침해 확정 여부를 검토한다. 한 사례의 통과를 일반적인 AI 분석 품질 입증으로 확대하지 않는다.

## 10. 증거와 출시

실행 결과는 `artifacts/completion/<run-id>/`에 사설 파일로 남기고 생성 산출물은 Git에서 제외한다. 요약 문서에는 커밋, 환경, 실행 명령, 수치, 실패와 재실행 결과를 남긴다. 원본 로그와 키는 커밋하지 않는다. 새 산출물 경로를 추가할 때 기존 `AGENTS.md` 및 `.hov/` ignore 규칙을 유지한다.

기존 `operations-validation.md`의 과거 측정은 그대로 두고 새 결과와 날짜를 추가한다. CI가 구성됐다는 사실과 실제 실행 성공을 구분한다. 장시간 실행을 위한 수동 workflow 또는 외부 실행 절차를 추가하며 일반 PR 테스트에서 72시간 작업을 실행하지 않는다.

스키마 6 배포물로 업그레이드한 홈은 구버전에서 직접 열지 않는다. 롤백은 작업자를 모두 중지한 뒤 migration 전 백업 묶음과 그에 맞는 프로그램 버전을 복원하는 절차다. 업그레이드 이후 기록이 롤백으로 사라질 수 있음을 표시하고 필요한 사건 보고서를 먼저 보존하도록 안내한다.

## 11. 위험과 설계 검토 조건

| 위험 | 대응과 통과 조건 |
| --- | --- |
| UI가 Repository 구현에 직접 의존해 추출 범위가 커진다 | gateway 인터페이스를 먼저 고정하고 독립 TUI 회귀를 통과한 뒤 연결 UI를 전환 |
| 온라인 정리가 수집과 경쟁한다 | 짧은 트랜잭션과 배치 조절. 실제 90일 데이터 및 지속 입력 중 목표 지연 확인 |
| 레거시 알림이 이미 누락됐거나 전달 상태를 알 수 없다 | ID 대조와 reconciliation 상태. 조용한 정상 처리 금지 |
| 복원 후 이전 요청이나 유료 작업이 재실행된다 | restore generation 확인과 명령 영수증. 유료 작업 자동 재요청 금지 |
| 설정 파일과 DB에 걸친 변경이 중간에 끊긴다 | revision 및 재조정 상태를 기록하고 재시작 시 확정 저장값으로 복구 |
| 플랫폼 소켓 자격증명 검증이 다르다 | macOS/Linux 실제 프로세스 검사 완료 전 제어 모드 지원 선언 금지 |
| 보호 기록과 백업이 계속 증가한다 | 보호 데이터의 용량을 분리해서 표시하고 명시적 백업 정리 제공. 무제한 보존을 무료 용량으로 취급하지 않음 |

이 기술안은 구현 시작 시 상세 타입과 트랜잭션 경계를 코드로 검증한다. 핵심 계약을 바꿔야 하면 PRD 인수 조건과 실행 계획도 함께 갱신한다. 목표를 낮춰 실패를 통과로 바꾸는 수정은 변경 사유와 검토 기록 없이 하지 않는다.
