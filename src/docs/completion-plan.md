# SocketClaw 완성 릴리스 실행 계획

작성일: 2026-09-29

상태: 기능 구현 및 로컬 검증 진행 완료분 반영, 출시 게이트 미완료

연결 문서: [PRD](completion-prd.md), [TRD](completion-trd.md)

실제 반영 내용과 실행 결과는 [구현 및 검증 보고서](completion-report.md)에 기록한다.
W-01부터 W-09까지의 주요 기능을 구현했다. W-10은 로컬 검사와 패키지 검증을 진행했고,
W-11의 실행 도구와 수동 CI를 추가했다. 72시간 검증과 외부 사용자 과업을 끝내기 전에는
W-12의 전체 완료 또는 출시 가능 판정을 내리지 않는다.

## 1. 목표와 종료 범위

이번 작업은 v0.6.0의 기능을 완성하는 안정화 릴리스다. 알림 복구 결함을 수정하고, 백그라운드 수집 중 사건을 끝까지 처리하도록 연결한다. 이와 함께 온라인 기록 정리와 서비스 상태 조회를 보완하고 실제 운영 및 배포 검증을 끝낸다.

앞선 검토에서 제기한 문제는 모두 아래 작업에 배정한다. 별도의 요청이 없는 기능 확장은 받지 않으며, 실행 중 발견한 결함은 이 사용자 흐름과 데이터 신뢰성에 영향을 주는지로 포함 여부를 결정한다.

| 문제 | PRD 요구사항 | 작업 |
| --- | --- | --- |
| 복원 후 알림 누락과 정상처럼 보이는 상태 | FR-01, FR-02, FR-07 | W-01, W-02, W-07 |
| 상시 감시와 사건 처리 단절 | FR-03, FR-04, FR-05, FR-10 | W-03, W-04, W-05 |
| 반복 정리 및 전체 백업 누적 | FR-06, FR-07 | W-06, W-07 |
| 최근 500건에 의존하는 서비스 상태 | FR-08 | W-08 |
| 제품 설명과 실제 수집 범위 차이 | FR-09 | W-09 |
| 장기 운영, 탐지 유용성 및 사용자 과업 근거 부족 | FR-11 및 NFR 전체 | W-10, W-11, W-12 |

## 2. 작업 순서와 의존성

```text
W-00 기준 고정
  → W-01 회귀 재현 및 스키마 계약
  → W-02 알림 원자성 및 레거시 이전
  → W-03 공용 애플리케이션 서비스
  → W-04 로컬 제어 서버
  → W-05 운영 제어 TUI
  → W-06 온라인 기록 정리
  → W-07 복원 및 백업 관리
  → W-08 서비스 상태 조회
  → W-09 범위 안내와 운영 문서
  → W-10 통합 및 배포 후보 검증
  → W-11 운영 검증과 사용자 과업
  → W-12 출시 판정
```

W-08은 W-01에서 스키마 계약을 정한 뒤 앞당겨도 된다. W-06의 저장소 로직은 W-03 이후 구현할 수 있지만 사용자 제어 경로는 W-04와 연결한다. 이는 기술적 의존성 설명이며 이번 계획에서 별도 에이전트 위임이나 병렬 작업을 실행하지 않는다.

## 3. 작업 명세

### W-00. 기준 고정과 개발 환경 확인

- 현재 HEAD와 깨끗한 작업 상태, 테스트 실행 환경을 기록한다.
- `uv sync --dev --locked`로 환경을 맞추고 기존 품질 검사 및 배포 workflow를 확인한다.
- 실제 사용자 홈을 변경하지 않는 테스트용 홈과 로컬 webhook 수신기를 준비한다.
- 기준 테스트 662개와 snapshot 36개는 과거 결과로 기록한다. 새 실행 결과는 구분한다.
- 현재 스키마 1~5 fixture와 v0.6.0 설치 패키지를 확보하고 migration 전후 비교용 자료를 고정한다.

완료 조건: 기준 커밋과 재현 명령이 남고 테스트용 저장소를 실제 홈과 분리했다.

### W-01. 실패 회귀와 데이터 계약

대상: `tests/integration`, `tests/unit`, `storage.py`, `migrations.py` 설계.

- 실제 SQLite backup/restore로 알림 누락을 재현하는 회귀 테스트를 추가한다.
- 서비스 관측 1개 뒤에 다른 시스템 이벤트 1만 개가 있는 fixture를 만든다.
- 알림 outbox와 명령 영수증, 정리 작업 및 서비스 인덱스의 스키마 6 계약을 확정한다.
- migration 중간 종료, 복원 generation과 legacy 알림 reconciliation의 상태 전이를 테스트로 명시한다.

완료 조건: 현재 결함을 설명하는 재현이 실패하고, 기대 동작이 PRD와 일치한다. 재현용 실패 테스트를 보호 브랜치에 단독 병합하지 않고 수정과 묶거나 작업 브랜치에서 유지한다.

### W-02. 알림 저장과 레거시 이전

대상: `notifications.py`, `incident_store.py`, `storage.py`, `migrations.py`, `doctor.py`.

- 사건 전이와 delivery 생성에 같은 DB 트랜잭션을 사용한다.
- claim과 lease, 안정적인 전달 ID 및 재시도 상태를 구현한다.
- 기존 notifications.db를 ID 기준으로 대조해 이전한다. 누락 또는 불확실한 이력은 상태로 드러낸다.
- 채널 비활성화와 목적지 변경 시 pending 항목을 잘못된 주소로 전송하지 않는다.
- 작업자 상태와 오류를 `notification-status`, Health 및 doctor에 노출한다.

완료 조건: T-01~T-03 통과. 새 사건 저장과 알림 enqueue 사이의 강제 종료에서 누락이 없고 기존 홈을 반복 이전해도 중복 import가 없다.

### W-03. 공용 운영 서비스 추출

대상: `ui/app.py`, 새 `application.py`, 새 `gateway.py`, 저장소 인터페이스.

- UI에 있는 조사 수명과 설정 변경을 소유자 서비스로 이전한다.
- 사건 편집과 응답 검토, 유지보수 예외 및 내보내기를 공용 진입점으로 묶는다.
- DB 명령의 영수증과 도메인 변경을 함께 커밋할 unit-of-work를 도입한다.
- 독립 TUI를 InProcessGateway로 전환하고 기존 취소 및 종료 보장을 유지한다.

완료 조건: 독립 TUI 전체 회귀 통과. 도메인 작업을 Textual App 인스턴스 없이 테스트할 수 있다. 이 단계에서 연결 UI를 구현하지 않아도 기존 사용 흐름이 유지된다.

### W-04. 로컬 제어 서버와 클라이언트

대상: 새 `control.py`, `gateway.py`, `cli.py`, 프로세스 통합 테스트.

- Unix 소켓 경계와 프로토콜 v1, 기능 협상 및 요청 제한을 구현한다.
- 같은 UID 검증과 홈 잠금, 오래된 소켓 정리 및 세션 nonce를 구현한다.
- 재전송 안전성, 충돌 응답과 작업 결과 조회를 구현한다.
- 긴 작업은 영속 ID를 반환하며 클라이언트 연결 수명과 분리한다.
- restore generation이 다른 요청을 거절하고 미지원 버전을 일찍 차단한다.

완료 조건: T-05와 T-13 통과. 실제 macOS/Linux의 두 프로세스가 연결되고 권한 및 프로토콜 오류가 저장소 변경 없이 끝난다.

### W-05. 수집을 유지하는 사건 처리 화면

대상: `ui/attached.py`, `ui/app.py`, 관련 사건 및 설정 화면, `cli.py`.

- `attach --tui --control`을 추가하고 기존 읽기 전용 명령은 유지한다.
- 공용 화면에서 사건 상세, 메모, 조치 기록과 검증, 종료 및 내보내기를 제공한다.
- AI 문맥 미리보기와 명시적 요청, 재시도 및 진행 상태를 연결한다.
- 설정과 규칙, 로그 및 서비스 관리를 소유자 요청으로 처리한다.
- 연결 종료와 수집 종료를 구분하고 재연결 시 초안과 선택을 유지한다.

완료 조건: T-04~T-06 및 T-10의 연결 시나리오 통과. 일반 TUI와 연결 TUI 모두 API 키 없이 U-02의 사건 처리 과정을 완료한다.

### W-06. 온라인 기록 정리

대상: 새 `maintenance.py`, `storage.py`, `cli.py`, 정리 UI.

- 읽기 전용 미리보기와 적용 작업을 분리한다.
- 일관된 백업의 watermark로 대상 범위를 고정하고 검증된 백업 하나를 재사용한다.
- 짧은 삭제 트랜잭션과 진행 상태 저장, 취소 및 재개를 구현한다.
- 동시 사건 편집과 조사의 참조를 삭제 직전에 다시 검사한다.
- 정리 중 수집과 서비스 검사 지연을 측정하고 배치 크기를 조정한다.

완료 조건: T-07 통과. 중간 종료 후 같은 작업을 재개해도 대상 범위가 늘어나지 않고 보호 증거 및 수집 checkpoint가 유지된다.

### W-07. 백업 관리와 복원

대상: `maintenance.py`, `migrations.py`, `cli.py`, `doctor.py`, 운영 문서.

- 백업 목록과 pin, 명시적 prune 미리보기 및 적용을 제공한다.
- 해시와 SQLite 무결성을 검사하는 `db restore`를 구현한다.
- 현재 홈 구조 백업과 복원 journal로 중간 실패에서 복구한다.
- v5 이하 백업의 알림 대조, 설정 지문 불일치와 복원 generation 처리를 연결한다.
- 실제 디스크 고갈 상황을 격리 환경에서 검증한다.

완료 조건: T-02, T-07, T-08 통과. 90일 규모의 정리 대상 전체를 한 작업으로 처리하고 백업 생성이 배치마다 반복되지 않는다. 복원 뒤 첫 새 사건 알림이 전달된다.

### W-08. 서비스 상태의 정확성

대상: `storage.py`, `probes/services.py`, `ui/services.py`, `health.py`.

- 서비스 ID 인덱스와 최신 관측 조회 API를 구현한다.
- 측정 결과와 신선도, 수집 상태 및 설정 일치 여부를 분리한다.
- 정책 지문에 timeout과 기대 응답 조건을 반영하고 변경 시 확인 streak을 초기화한다.
- 과거 정보 부족과 재등록을 명시적으로 처리하고 마지막 관측을 정리 보호 대상에 넣는다.

완료 조건: T-09 통과. 기록 규모와 다른 서비스의 빈도 때문에 마지막 관측이 화면에서 사라지지 않는다.

### W-09. 제품 범위와 운영 안내

대상: README, onboarding, Overview, 도움말, 서비스 템플릿, `operations-validation.md`.

- 지정 대상 감시 도구라는 제품 정의를 첫 화면과 문서에 일치시킨다.
- 지원하지 않는 로그 소스와 권한 부족을 구분하고 서비스 전용 시작 경로를 확인한다.
- 독립 실행과 읽기 전용 연결, 운영 제어 연결의 차이를 설명한다.
- 백업과 정리의 용량 한계, 복원 중복 알림 및 rollback 절차를 기록한다.
- 사용자에게 구현 용어를 요구하지 않는 오류 문구와 다음 행동을 제공한다.

완료 조건: FR-09와 T-10 통과. 문서의 명령을 격리 홈에서 직접 실행할 수 있고 지원 범위 과장이 없다.

### W-10. 통합 검증과 release candidate

- 전체 단위 및 통합 테스트, snapshot, 정적 검사와 잠금 의존성 검사를 실행한다.
- 의존성 감사와 wheel/sdist 빌드, 별도 환경 설치 및 실제 PTY 검사를 실행한다.
- 기존 Linux/macOS, Python 3.11/3.14 매트릭스를 통과한다.
- macOS arm64와 x86_64 배포물을 빌드해 초기 설치, v0.6.0 업그레이드, 재실행 및 복구를 확인한다.
- 자격증명과 원본 증거가 IPC 오류, 공유 보고서 및 검증 산출물에 노출되지 않는지 검사한다.
- T-01~T-10, T-12의 mock 부분 및 T-13 증거를 연결한다.

완료 조건: 출시 후보 커밋과 배포물 해시를 고정한다. 실패를 baseline 갱신이나 skip으로 숨기지 않는다.

### W-11. 장기 운영과 사용자 과업

- TRD의 동일 프로필로 macOS arm64와 Linux x86_64에서 각각 72시간 실행한다.
- 100건/초 30분 부하와 온라인 정리를 포함하고 정상 구간 및 장애 주입 결과를 구분한다.
- 정답을 선언한 정상/이상 시나리오의 사건과 알림 수를 대조한다.
- 구현 담당 외 사용자 최소 1명의 과업을 관찰하고 개입 여부와 소요 시간을 기록한다.
- 키와 실행 허용이 있으면 변경된 조사 경로로 라이브 조사 1회를 수행한다. 그 외에는 해당 게이트를 미검증으로 남긴다.
- 결함을 수정하면 관련 자동 검사와 운영 검증을 다시 수행한다. 수집, 저장, IPC 또는 알림 수명에 영향을 주는 수정이면 72시간을 새로 시작한다.

완료 조건: FR-11 및 NFR 전체를 측정 결과로 판정한다. 시작만 한 실행이나 중간 결과를 통과로 기록하지 않는다.

### W-12. 출시 판정과 종료

- 요구사항별 증거 목록과 잔여 결함을 검토한다.
- 필수 결함이 0건인지 확인하고 사용자 과업의 막힘을 재검증한다.
- 실제 지원 환경과 알려진 제한, migration 및 rollback 안내를 최종 릴리스 노트에 작성한다.
- 버전과 패키지 상태를 검증 결과에 맞춰 정한다.
- 배포 후 새 설치와 업그레이드 smoke를 확인하고 마무리 보고서를 남긴다.

완료 조건: 아래 출시 게이트를 전부 통과했다. 구현 완료와 배포 실행은 구분하며 이번 문서 작성 요청만으로 실제 배포를 진행하지 않는다.

| G-04 운영 안정성 | 고정 후보의 72시간 두 환경 및 지속 부하 측정 | 보고서에서 개별 판정 |
| G-05 탐지와 사용성 | 고정 시나리오 기대값 일치, 사용자 과업 완료 | 보고서에서 개별 판정 |
| G-06 AI 경로 | mock 회귀와 명시적 라이브 조사, 키 노출 없음 | 보고서에서 개별 판정 |
| G-07 제품 설명 | 지원 범위, 설정과 실행 모드, 백업 및 복원 안내 일치 | 보고서에서 개별 판정 |

품질 요구사항은 NFR-01을 G-01에, NFR-02와 NFR-03을 G-02/G-04에 연결한다. NFR-04와 NFR-05는 G-04, NFR-06은 G-02/G-05, NFR-07은 G-01/G-03/G-06에서 판정한다. 측정 방법은 TRD의 품질 검증표를 따른다.

출시를 막는 결함은 증거 손실, 알림의 조용한 누락, 승인 없는 유료 요청, 권한 경계 위반과 필수 과업 차단이다. 성능 목표 미달도 해당 지원 프로필의 출시를 막는다. 문구나 정렬 같은 경미한 문제만 영향과 우회 방법을 적고 남길 수 있다.

## 5. 예상 규모와 필요한 실행 환경

아래는 구현 전 계획용 추정이다. 담당자 1명이 순차 진행하는 기준이며 일정 약속이 아니다. 코드 추출 범위와 migration 복잡도를 W-03 종료 시 다시 추정한다.

| 묶음 | 예상 작업일 |
| --- | ---: |
| W-00~W-02 기준과 알림 복구 | 3~5 |
| W-03~W-05 공용 서비스와 운영 제어 | 6~10 |
| W-06~W-08 정리, 복원 및 상태 조회 | 5~8 |
| W-09~W-10 문서와 통합 검증 | 2~4 |
| W-11~W-12 실행 준비, 분석과 출시 판정 | 2~4 |
| 합계 | 18~31 작업일 |

72시간 실행은 별도의 경과 시간이 필요하다. 두 환경을 동시에 운용하면 최소 3일, 순차 운용하면 최소 6일이며 결함 수정 후 재실행 시간은 추가된다. 소규모 마지막 수정으로 가정하고 며칠 안에 종료를 약속하지 않는다. 가장 큰 작업은 기존 TUI 내부의 운영 로직을 상시 수집 프로세스로 옮기는 부분이다.

필요한 자원은 계속 켜둘 macOS arm64와 Linux x86_64 환경, Intel macOS 배포 검증 runner, 수 GB 이상의 격리 테스트 공간, 실제 사용자 과업 참여자 1명이다. AI 검증에는 사용할 수 있는 키와 유료 실행 허용이 필요하다. 자원이 없으면 자동 테스트를 완료해도 해당 운영 게이트는 미검증으로 유지한다.

## 6. 산출물과 변경 관리

최종 산출물은 수정 코드와 migration, 회귀 테스트, 갱신된 운영 문서, 배포 후보와 최종 검증 보고서다. 보고서에는 요구사항 ID마다 실행 결과를 연결한다. 생성된 상세 로그는 사설 산출물로 보관하고 redaction한 요약만 저장소에 남긴다.

문서 작성 시점에는 구현과 72시간 검증을 수행하지 않았다. 이번 PRD와 TRD의 새 명령, 모듈 및 수치는 모두 목표다. 구현 중 계약을 변경하면 세 문서를 함께 갱신하고 이유를 남긴다. 사용자 시나리오를 줄이는 변경으로 완료 상태만 만들지 않는다.

모든 게이트를 통과한 이후에는 새 기능을 추가하지 않고 해당 범위를 종료한다. 네이티브 로그 수집이나 원격 운영 같은 확장은 후속 버전의 별도 과제로 다룬다.
