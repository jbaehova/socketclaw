# SocketClaw 완성 릴리스 PRD

작성일: 2026-09-29

상태: 기능 구현 반영, 출시 인수 조건은 개별 검증 중

기준: v0.6.0, 커밋 `a476db3`

연결 문서: [실행 계획](completion-plan.md), [TRD](completion-trd.md)

구현 상태와 검증 근거: [구현 및 검증 보고서](completion-report.md). 아래 인수 기준은 구현 여부와 별도로 유지한다.

## 1. 제품 정의와 이번 릴리스의 목표

SocketClaw는 사용자가 지정한 호스트와 서비스, 파일 로그를 감시하고 이상 징후의 증거를 보존하는 개인 운영 도구다. 사용자는 증거를 검토한 뒤 직접 조치하고 그 결과를 사건에 기록한다. AI 조사는 선택 기능이며 기본 운영 흐름은 API 키 없이도 끝까지 진행된다.

이번 릴리스에서는 이미 구현한 기능을 일상 운영과 복구 상황에서도 끝까지 사용할 수 있게 한다. 특히 백그라운드 감시를 중단하지 않고 사건을 처리하며, 오래 쌓인 기록을 정리하고, 백업을 복원한 뒤에도 알림과 상태 표시를 신뢰할 수 있어야 한다.

완성의 기준은 아래 사용자 흐름이 실제 환경에서 성립하는 것이다.

> 설치와 감시 범위 확인 → 수집 시작 → 이상 발견과 알림 → 증거 조사 → 사용자 조치 기록 → 후속 관측 확인 → 사건 종료와 보고서 보존 → 기록 정리와 장애 복구

제품 전체에 대한 무결함 선언이나 모든 침해의 탐지를 약속하지 않는다. 이번 문서의 요구사항과 검증 조건을 충족한 버전을 완성 릴리스로 판단한다. 버전 번호는 검증 결과를 확인한 뒤 결정하며, 현재의 Beta 표기를 먼저 제거하지 않는다.

## 2. 확인한 상태와 해결할 문제

| ID | 확인 수준 | 현재 상태 | 사용자 영향 |
| --- | --- | --- | --- |
| P-01 | 재현한 결함 | 증거 DB 복원 후 별도 알림 DB의 행 번호 커서가 앞서 남는다 | 새 사건 알림이 누락돼도 실패가 표시되지 않는다 |
| P-02 | 코드에서 확인한 제약 | `monitor`와 일반 TUI는 같은 쓰기 잠금을 사용한다. `attach --tui`는 읽기 전용 목록이다 | 상시 수집을 유지하면서 사건을 조사하고 처리하는 경로가 끊긴다 |
| P-03 | 코드와 측정 문서에서 확인 | 정리 명령은 기본 1만 건마다 전체 백업을 만들고 쓰기 잠금을 요구한다 | 대량 정리의 반복 실행과 백업 누적 부담이 크다 |
| P-04 | 코드에서 확인한 제약 | Services 화면은 전체 시스템 이벤트 최근 500건에서 상태를 찾는다 | 다른 이벤트가 많으면 해당 서비스의 마지막 상태가 화면에서 사라진다 |
| P-05 | 제품 범위의 불일치 가능성 | 파일 로그와 지정한 네트워크 대상만 수집한다 | 시스템 전체 보안 상태를 보장하는 도구로 오해할 수 있다 |
| P-06 | 검증 근거 부족 | 자동 테스트와 짧은 부하 측정은 있지만 며칠간의 운영 및 사용자 과업 측정은 별도다 | 장기 운영의 안정성과 실제 탐지 유용성을 아직 입증하지 못했다 |

기준 커밋에서 로컬 테스트 662개와 시각 비교 36개가 통과했다. 유료 라이브 테스트 1개는 실행 조건에 따라 건너뛰었다. 정적 검사와 PTY 검사도 통과했고 GitHub의 Linux/macOS 품질 검사 및 macOS 양쪽 아키텍처 빌드도 성공했다. 다만 이 결과는 변경 후 구현의 통과 근거로 재사용할 수 없다.

## 3. 대상 사용자와 지원 범위

주 사용자는 자신의 컴퓨터나 소규모 서버를 관리하는 개발자다. 한 운영체제 계정이 하나의 애플리케이션 홈을 관리한다. 같은 계정의 여러 화면이 연결될 수 있지만 여러 사용자 사이의 권한 관리나 원격 제어는 제공하지 않는다.

| 항목 | 이번 릴리스의 약속 |
| --- | --- |
| macOS | Apple Silicon과 Intel 배포물 설치 및 실행 지원 |
| Linux | 소스 설치와 로컬 운영 제어 지원. 실제 검증 환경을 명시 |
| Windows | 기존 실행 경로에 불필요한 회귀를 만들지 않는다. 완성 릴리스의 검증된 상시 운영 대상으로 선언하지 않는다 |
| 수집 | 설정한 네트워크 대상과 서비스, 지원하는 파일 로그 형식 |
| 미지원 수집 | journald 직접 수집과 macOS unified logging 직접 수집 |
| 조치 | 사람이 수행한 조치 및 검증 결과 기록. 모델 명령 실행과 자동 방화벽 변경은 범위 밖 |
| AI | 명시적으로 요청할 때만 조사. 연결 실패 중에도 로컬 운영 가능 |

웹 UI, 원격 에이전트, 다중 사용자 권한 체계는 추가하지 않는다. 새로운 탐지 제품군이나 운영체제별 네이티브 로그 수집도 이번 마무리 범위에 넣지 않는다.

## 4. 사용자 시나리오

### U-01. 처음 설치한 사용자가 실제 감시 범위를 이해한다

사용자는 파일 로그가 없는 환경에서도 서비스만 설정해 시작한다. 첫 실행과 Overview에는 설정된 감시 대상 수와 실제 수집 성공 여부가 따로 표시된다. 읽을 수 없는 로그와 미지원 소스는 그 이유를 보여준다. 관측이 없다는 이유로 정상 상태를 표시하지 않는다.

### U-02. 상시 수집 중 발생한 사건을 끝까지 처리한다

사용자는 `socketclaw monitor`를 실행하고 알림을 받는다. 이어서 `socketclaw attach --tui --control`로 연결해 사건 상세와 관련 증거를 확인한다. 필요하면 AI 조사 전에 전송할 내용을 미리 보고 직접 요청한다. 사건을 확인 상태로 바꾸고 조치 결과를 기록한 뒤 후속 관측을 연결해 검증한다. 마지막으로 사건을 종료하고 보고서를 내보낸다. 이 과정에서 수집 프로세스를 중지하지 않는다.

`attach --tui`는 기존의 읽기 전용 의미를 유지한다. 조작 가능한 연결 화면에는 운영 제어 모드임을 표시하고, 화면 종료는 연결만 닫는다. 수집 중지는 별도 명령과 확인 단계로 제공한다.

### U-03. 연결이 끊겨도 작업 결과와 초안을 확인한다

요청 직후 연결이 끊기면 성공이나 실패를 임의로 표시하지 않는다. 재연결 후 같은 요청의 처리 결과를 조회하고, 이미 저장한 메모나 유료 조사를 다시 생성하지 않는다. 아직 보내지 않은 편집 내용은 현재 화면 세션에서 보존한다. 클라이언트 프로세스 자체가 종료된 뒤의 초안 복원은 약속하지 않는다.

### U-04. 오래 쌓인 기록을 한 번의 작업으로 정리한다

사용자는 정리 대상을 미리 보고 예상 백업 용량을 확인한다. 적용하면 검증된 백업 하나를 만든 뒤 대상 기록을 작은 단위로 정리한다. 진행 상황과 남은 건수가 표시되고 중간에 취소하거나 재개할 수 있다. 보호 대상 증거는 남으며, 감시와 사건 처리는 계속된다.

### U-05. 장애 후 백업을 복원하고 감시를 재개한다

사용자는 수집을 중지하고 백업을 검증한 뒤 복원한다. 복원 시점 이후의 로컬 기록이 사라진다는 사실과 알림이 중복될 가능성을 확인한다. 재시작 후 새 사건은 알림 대상이 되며, 복원 전 처리 위치 때문에 건너뛰지 않는다. 복구 상태와 실패 사유는 `doctor`와 운영 화면에서 확인한다.

## 5. 기능 요구사항

P0는 데이터 보존과 알림 신뢰성을 위한 필수 수정이다. P1도 이번 완성 릴리스의 필수 범위이며 선택 개선을 뜻하지 않는다.

| ID | 우선순위 | 요구사항 | 인수 조건 |
| --- | --- | --- | --- |
| FR-01 | P0 | 사건과 알림 처리 상태를 함께 복원한다 | 과거 백업 복원 후 첫 새 사건부터 알림이 생성된다. 송신 직후 장애의 중복 가능성은 표시하고 식별키를 유지한다 |
| FR-02 | P0 | 알림 장애를 관측한다 | 미전송 건수, 마지막 실패, 재시도 예정과 작업자 생존 상태를 표시한다. 상태 조회 불가를 정상 0건으로 표시하지 않는다 |
| FR-03 | P1 | 연결 화면에서 사건 처리 전 과정을 제공한다 | 상세 조회부터 조치 기록, 검증, 종료, 내보내기까지 U-02를 수집 중단 없이 완료한다 |
| FR-04 | P0 | 연결 재시도와 동시 편집을 안전하게 처리한다 | 같은 요청은 한 번만 반영된다. 상태 충돌은 사용자가 검토하며 초안을 유지한다. 연결 종료는 수집이나 진행 중 조사를 취소하지 않는다 |
| FR-05 | P1 | 연결 화면에서 운영 설정을 관리한다 | 대상과 서비스, 로그 설정을 변경하고 수집을 일시정지하거나 재개한다. 규칙과 유지보수 예외도 기존 검증 규칙으로 저장한다 |
| FR-06 | P1 | 온라인 기록 정리를 제공한다 | 한 작업의 고정된 대상 범위를 자동으로 분할 처리한다. 취소와 재시작 뒤 진행 위치를 유지하고 보호 대상은 삭제하지 않는다 |
| FR-07 | P0 | 백업과 복원 절차를 완성한다 | 검증된 백업만 사용한다. 공간 부족 시 삭제를 시작하지 않는다. 부분 복원 실패에서 원본을 회수할 수 있고 백업 관리 정책을 명시한다 |
| FR-08 | P1 | 서비스별 마지막 측정과 신선도를 정확히 표시한다 | 다른 이벤트 1만 건을 추가해도 마지막 측정이 유지된다. 설정 변경 전 결과와 오래된 결과를 현재 정상으로 표시하지 않는다 |
| FR-09 | P1 | 수집 범위와 운영 상태를 분명히 안내한다 | 설정됨, 수집 성공, 미지원, 권한 부족, 오래됨을 구분한다. 일반 실행과 백그라운드 실행의 차이를 첫 사용 안내에서 설명한다 |
| FR-10 | P1 | 오프라인 사건 처리 흐름을 보장한다 | API 키 없이 장애 발생부터 사건 종료 및 보고서 생성까지 완료한다. AI 기능 실패가 이 흐름을 차단하지 않는다 |
| FR-11 | P1 | 배포물 기준의 운영 검증을 남긴다 | 장시간 실행과 장애 주입, 실제 사용자 과업 결과를 커밋 및 실행 환경과 함께 기록한다 |

FR-03에는 기존 사건 확인, 재열기, 메모, 예외 관리, 응답 제안 검토를 포함한다. 조치 승인과 실제 실행 결과는 지금처럼 분리한다. AI 조사와 재시도도 명시적 사용자 요청으로만 시작한다.

## 6. 품질 목표와 출시 조건

아래 수치는 기존 측정 결과가 아닌 이번 릴리스의 목표다. 측정 장비와 프로필은 TRD에 고정하며 달성하지 못한 수치를 통과로 기록하지 않는다.

| ID | 기준 |
| --- | --- |
| NFR-01 | 사건 변경과 알림 생성이 원자적으로 저장된다. 프로세스 장애로 커밋된 사건의 알림이 조용히 사라지는 경우는 0건이다 |
| NFR-02 | 정상 부하에서 연결 화면의 일반 조회와 짧은 변경 요청은 p95 1초 이내다. 긴 작업은 1초 안에 작업 ID를 반환한다 |
| NFR-03 | 정상 수집 중 저장 상태가 화면에 반영되는 시간은 5초 이내다. 연결 종료 또는 수집기 정지를 10초 이내에 구분해 표시한다 |
| NFR-04 | 72시간 운영 검증에서 설명되지 않는 증거 누락, 중복 조작, 비정상 종료가 없어야 한다. 주입한 장애의 관측 불가 구간은 별도로 기록한다 |
| NFR-05 | 100건/초의 합성 로그 입력을 30분간 처리한 뒤 30초 안에 처리 대기가 해소된다. 동시에 실행하는 1초 주기 서비스 검사는 정상 구간 p95 간격 2초 이내다 |
| NFR-06 | 80×24와 120×36에서 U-02의 모든 필수 동작을 키보드로 완료한다. 화면 크기 변경과 재연결 후 선택 및 세션 초안이 유지된다 |
| NFR-07 | 기존 비밀정보 보호, 원본 증거 보존, 명시적 AI 요청 및 단일 쓰기 소유 원칙을 유지한다 |

72시간 검증만으로 탐지 성능 전체를 증명했다고 주장하지 않는다. 별도로 정상 상황과 알려진 이상 상황의 정답을 붙인 시나리오를 실행해 예상 경보를 확인한다. 실제 사용 중 불필요한 경보가 반복되면 원인과 조정 결과를 기록한다.

## 7. 완성 판정

다음 항목을 모두 만족해야 이번 범위를 종료한다.

- FR-01부터 FR-11까지 인수 조건을 충족하고 테스트 또는 실행 증거를 연결한다.
- 일반 TUI와 운영 제어 연결 TUI에서 같은 사건 처리 시나리오를 완료한다.
- 72시간 운영 검증과 30일/90일 규모의 기록 정리 및 복구 검증을 통과한다.
- 구현 담당 외 사용자 최소 1명이 설치와 감시 시작, 사건 처리, 보고서 생성을 진행자 개입 없이 완료한다. 소요 시간과 막힌 지점을 기록한다.
- 데이터 손실, 알림 누락, 보안 경계 위반과 필수 흐름 차단 결함은 0건이다. 경미한 잔여 문제는 영향과 우회 방법을 공개한다.
- 지원 범위와 제한, 백업 복구 방법을 실제 구현과 일치시키고 배포물을 검증한다.

유료 AI 검증은 기존 실행 기록과 새 구현 검증을 구분한다. 이번 경로 변경 후 최소 한 번의 명시적 라이브 조사를 수행하는 것이 AI 기능의 출시 조건이다. 키나 실행 승인이 확보되지 않으면 해당 조건은 미검증으로 남기며, 제품 전체를 검증 완료로 표시하지 않는다.
